> **Scope note:** This audit was generated by inspecting the actual manifests and git tracking state
> in this repository (no external cluster dump was supplied) as of **2026-07-05**, branch `main`.
> Evidence is drawn from file contents, `git status`/`git log` tracking state, embedded
> `kubectl.kubernetes.io/last-applied-configuration` annotations (a signature left by `kubectl apply`

   declare `Installation/default` for Calico with **contradictory specs** — whichever was `kubectl apply`'d
   last silently won, and neither file is the single source of truth. This is drift already in progress.

   reverted per the file's own comment — meaning **the live cluster's mTLS mode and the repo's

4. No secret management layer (Sealed Secrets / External Secrets Operator) exists anywhere — every
   credential is a raw `v1/Secret` with base64 data checked into a file on disk.

## 3. 🚀 ArgoCD & GitOps Migration Pathway

### 3.1 Repository structure recommendation

You already have the right shape started (`argocd/application-slo.yaml` as a standalone Application).
Scale that into an **App-of-Apps** root, since your workloads are a fixed, small set of distinct apps
rather than a fleet needing templated generation (an `ApplicationSet` would be overkill for 6–7 apps —
reserve that pattern for the `per-node-pools.yaml` / node-onboarding case below, where a `List` generator
keyed on node name is actually a good fit).

```
argocd/
├── root-app.yaml                 # App-of-Apps: points at argocd/apps/
├── apps/
│   ├── slo-rules.yaml             # (existing, just move it here)
│   ├── cluster-networking.yaml    # Calico + MetalLB + per-node IPPools
│   ├── ase-market.yaml            # wraps helm/ase-market
│   ├── istio-mesh.yaml            # IstioOperator + Gateway/VS/PeerAuth
│   ├── teleport-agent.yaml        # wraps teleport/ Helm values
│   ├── freqtrade.yaml             # freqtrade namespace/deployments
│   └── rbac-users.yaml            # RBAC/ Role + RoleBinding only — NOT keys/certs
```

Two things to fix **before** wiring any of this up (both already flagged in Section 2):
- Delete or move `helm/ase-market/templates/read-pods-binding.yaml`'s placeholder subject, and decide
  whether `pod-reader`/`read-pods-binding` belong in this chart at all — right now they're a stray
  tutorial artifact, not app config.
- Replace `registry-secret.yaml` and `tls-secret.yaml` with either **Sealed Secrets** (simplest for a
  single-operator homelab — encrypt with `kubeseal`, commit the ciphertext, safe in git) or **External
  Secrets Operator** pointed at a local Vault/1Password. Do this *before* the ArgoCD Application exists,
  or ArgoCD will happily sync live plaintext secrets and mark them "Synced" forever.

### 3.2 Sample `Application` manifest — `ase-market` (Helm chart, adopting the existing release)

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: ase-market
  namespace: argocd
  finalizers:
    - resources-finalizer.argocd.argoproj.io
  labels:
    app.kubernetes.io/part-of: homelab
spec:
  project: default
  source:
    repoURL: https://github.com/abutouq/homelab.git
    targetRevision: main
    path: helm/ase-market
    helm:
      valueFiles:
        - values.yaml
      releaseName: ase-market
  destination:
    server: https://kubernetes.default.svc
    namespace: ase-market-helm
  syncPolicy:
    # Start WITHOUT automated sync while adopting an existing release —
    # flip `automated` on only after the first manual sync shows zero diff.
    syncOptions:
      - CreateNamespace=false      # namespace already exists; avoid an ownership fight
      - ServerSideApply=true       # avoids "last-applied-configuration" annotation churn
      - PruneLast=true
    retry:
      limit: 3
      backoff:
        duration: 10s
        factor: 2
        maxDuration: 3m
  revisionHistoryLimit: 5
```

Once `argocd app diff ase-market` shows no unexpected changes, add:

```yaml
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```

### 3.3 Adopting existing live resources without downtime or recreation

The failure mode to avoid: ArgoCD computing a diff on a resource it's never seen, deciding fields
differ (even just annotation churn from `kubectl apply`'s strategic-merge vs. ArgoCD's apply method),
and recreating or restarting something that's currently healthy. Sequence for each app group in 3.1:

```bash
# 1. Confirm what's actually live vs. what's in the repo file, per resource —
#    do this BEFORE creating the Application. Zero diff output = safe to adopt as-is.
kubectl diff -f freqtrade/deployment-highfreq.yaml
kubectl diff -f k8s-services/calico-installation.yaml   # <-- expect this one to show drift; resolve first

# 2. For anything with drift (the Calico duplicate is the known case), pick ONE file as
#    source of truth and delete the other from the repo before going further:
git rm k8s-services/VXLAN.yaml   # or calico-installation.yaml — whichever matches live state
kubectl get installation default -o yaml > /tmp/live-calico.yaml   # diff against the survivor by hand

# 3. Create the Application with automated sync DISABLED first, so ArgoCD only compares,
#    it does not touch anything yet:
argocd app create ase-market \
  --repo https://github.com/abutouq/homelab.git \
  --path helm/ase-market \
  --dest-server https://kubernetes.default.svc \
  --dest-namespace ase-market-helm \
  --sync-policy none

# 4. Inspect the computed diff. This is the "will anything get recreated" gate:
argocd app diff ase-market

# 5. If the diff is clean (or only shows benign annotation differences), do a manual,
#    server-side sync — server-side apply avoids the client-side "last-applied-configuration"
#    3-way-merge that can trigger spurious recreates on resources kubectl previously touched:
argocd app sync ase-market --server-side

# 6. Only after a clean sync + a healthy app, turn on auto-sync + self-heal:
argocd app set ase-market --sync-policy automated --auto-prune --self-heal

# 7. Repeat steps 3-6 per app group. For resources ArgoCD should track but NOT be allowed to
#    delete if removed from git (e.g. the MetalLB IPAddressPool — deleting it live-migrates your
#    LoadBalancer IPs), pin that specific resource with:
kubectl annotate ipaddresspool main-pool -n metallb-system \
  argocd.argoproj.io/sync-options=Prune=false
```

For the node-onboarding case (`k8s-services/node-worker-0X.yaml`, `per-node-pools.yaml`), once you're
past initial adoption, that's the one spot in this repo that genuinely fits an `ApplicationSet` with a
`git` directory generator (`k8s-services/nodes/*.yaml`) — new worker nodes then get their `IPPool` +
label patch created automatically the moment their file is added to the repo, instead of the current
copy-paste-and-edit pattern visible across `node-worker-02/03/04.yaml`.
