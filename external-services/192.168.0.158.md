# 192.168.0.158 (worker-01)

Standalone Ubuntu host, **not** part of the Kubernetes cluster managed by
[ansible/hosts.ini](../ansible/hosts.ini) (masters `.157`, workers `.155`,
`.156`, `.159` — `.158` is absent). It has leftover `kubeadm.sh` /
`kube-flannel.yml` / `admin.conf` files under `/home/ubuntu`, apparently
from an earlier, abandoned attempt to make it a cluster node — treat
those as historical, not active.

It runs two Docker Compose stacks (pihole, monitoring) *and* it is the
self-hosted **Teleport control plane** for the whole homelab — see
[Teleport](#teleport-self-hosted-control-plane) below. That makes this
host more critical than "a couple of side services": if it's down,
`teleport.homebytes.space` is unreachable and so is everything proxied
through it (Grafana, pihole admin, the k8s cluster's Teleport app/kube
access, `ase-market`'s Teleport entry).

SSH: `ssh ubuntu@192.168.0.158`. The `ubuntu` user is in `sudo` (password
required, not passwordless) but **not** in `docker` — so `docker`/`docker
compose` commands need `sudo`, and there's no way to run them
non-interactively over SSH without the password.

  host's LAN IP.

## Locking down direct LAN access

Grafana, pihole admin, Prometheus, Loki, and (once deployed) LocalStack were
all previously published on `0.0.0.0`, meaning anyone on the LAN could reach
them directly, bypassing Teleport entirely. Their compose port mappings are
now `127.0.0.1:<port>:<port>` instead — Teleport's `app_service` reaches them
via `http://localhost:<port>/` on this same host, so that keeps working; LAN
access to those ports directly no longer does. DNS (`53`) and the Teleport
ports (`443`/`3025`/`3022`) are intentionally untouched — they need to stay
reachable from the LAN/cluster.

`ufw` alone would **not** have achieved this — Docker inserts its own
iptables rules ahead of `ufw`'s, so a `ufw deny <port>` typically doesn't
block a docker-compose-published port. Binding the publish itself to
`127.0.0.1` is the reliable fix.

**Applied and verified on 2026-07-09.** Reference commands, for redeploying
after future edits to these compose files:

1. Fix Prometheus's self-scrape target (breaks once 9090 is loopback-only,
   since it scraped itself via the public IP before this):
   ```
   sudo sed -i 's/192.168.0.158:9090/localhost:9090/' /data/monitoring/prometheus/prometheus.yml
   curl -X POST http://localhost:9090/-/reload
   ```
2. Deploy the pihole stack (`ubuntu` owns this dir, no `sudo` needed for the copy):
   ```
   scp external-services/pihole/docker-compose.yaml ubuntu@192.168.0.158:/home/ubuntu/pihole/docker-compose.yaml
   ssh ubuntu@192.168.0.158 'cd /home/ubuntu/pihole && sudo docker compose up -d'
   ```
3. Deploy the monitoring stack (`/data/monitoring` is root-owned, needs an extra hop):
   ```
   scp external-services/monitoring/docker-compose.yml ubuntu@192.168.0.158:/tmp/docker-compose.yml
   ssh ubuntu@192.168.0.158 'sudo cp /tmp/docker-compose.yml /data/monitoring/docker-compose.yml && cd /data/monitoring && sudo docker compose up -d'
   ```
4. Verified: loopback ports return `200`/`302`/`404` (real HTTP responses)
   locally but time out from another LAN client; DNS still resolves
   LAN-wide; both Teleport apps still load; Prometheus `/targets` shows all
   jobs `up`, including the self-scrape job. One thing this broke that
   wasn't obvious up front — Grafana's Prometheus datasource used the LAN IP
   instead of the Docker network and stopped working; see the datasource
   gotcha noted above.

Not covered by this pass: `node_exporter` (`9100`, all 5 cluster nodes) and
`pihole-exporter` (`9617`) stay LAN-reachable on purpose — Prometheus scrapes
them by IP across hosts/docker networks, so loopback-binding would break
monitoring. Restricting those to "only reachable from `192.168.0.158`" needs
real per-host firewall rules (via Ansible, across 5 nodes) — separate task.

### TLS certificate renewal

`teleport/renew-teleport-cert.sh` (repo copy:
[teleport/renew-teleport-cert.sh](teleport/renew-teleport-cert.sh); run
on the host itself, e.g. via cron) renews the `teleport.homebytes.space`
cert with Certbot's DNS-01 Cloudflare challenge and drops the result
into `/home/ubuntu/teleport-tls/`:

1. Pulls the Cloudflare API token from LocalStack Secrets Manager
   (`cloudflare-api-token`, see [Accessing LocalStack](#accessing-localstack-an-api-not-a-browser-app)
   above) and writes it to a `chmod 600` temp credentials file — Certbot's
   `--dns-cloudflare-credentials` flag takes a file path, not the raw
   token, and refuses world-readable files.
2. Runs `certbot certonly --non-interactive --agree-tos
   --register-unsafely-without-email --dns-cloudflare ...` for both
   `teleport.homebytes.space` and `*.teleport.homebytes.space`.
3. Copies `fullchain.pem`/`privkey.pem` into `/home/ubuntu/teleport-tls/`
   and restarts `teleport.service` to pick them up.

Requires Certbot plus the `certbot-dns-cloudflare` plugin on the host —
installed by [`ansible/install_awscli.yml`](../ansible/install_awscli.yml)
(needs `snap set certbot trust-plugin-with-root=ok` before the plugin
snap, or its flags come back as "unrecognized arguments").

**Scheduled via root's crontab**, confirmed working 2026-07-28:
```
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/snap/bin
59 5 * * * /home/ubuntu/renew-teleport-cert.sh >> /var/log/renew-teleport-cert.log 2>&1
```
Two gotchas that broke the first attempt: (1) invoking it as `/bin/sh
renew-teleport-cert.sh` ignores the script's `#!/bin/bash` shebang and
runs it under `dash`, which doesn't support `set -o pipefail` — call the
script directly instead, letting the shebang pick bash. (2) cron's
default `PATH` doesn't include `/snap/bin`, so `aws`/`certbot` (both
snap-installed) aren't found unless `PATH` is set explicitly in the
crontab. `ubuntu` has scoped `NOPASSWD` sudo (`/etc/sudoers.d/renew-teleport-cert`)
for `crontab` and for running this script directly, for
troubleshooting/verification without needing the interactive sudo
password.

### Accessing LocalStack (an API, not a browser app)

**CORS gotcha**: LocalStack rejects any request whose `Origin` isn't
`localhost`/`127.0.0.1` by default — hitting
`https://localstack.teleport.homebytes.space` directly (browser, or
`curl`) returns `403 Blocked CORS request from forbidden origin`, even
though Teleport itself authorized the session fine (check `app.session.start`
in the audit log to tell the two apart — a Teleport RBAC denial never
gets that far). Fixed via `EXTRA_CORS_ALLOWED_ORIGINS` in the compose
file, *not* `LOCALSTACK_HOST` (that only affects endpoint URL
construction, not CORS — see `localstack/config.py` in the image for the
actual list of recognized settings if this comes up again for a
different service).

Secrets Manager is an AWS API, not a web UI, so use `tsh proxy app`
instead of a browser anyway — traffic through the local tunnel targets
`localhost:4566` directly and was never affected by the CORS check:

```
tsh login --proxy=teleport.homebytes.space
tsh proxy app localstack --port=4566   # local tunnel, leave running

# in another terminal:
export AWS_ACCESS_KEY_ID=test AWS_SECRET_ACCESS_KEY=test AWS_DEFAULT_REGION=us-east-1
aws --endpoint-url=http://localhost:4566 secretsmanager list-secrets

# create a secret
aws --endpoint-url=http://localhost:4566 secretsmanager create-secret \
  --name pihole/api-password --secret-string 'whatever-the-real-value-is'

# read it back
aws --endpoint-url=http://localhost:4566 secretsmanager get-secret-value \
  --secret-id pihole/api-password --query SecretString --output text

# update it later
aws --endpoint-url=http://localhost:4566 secretsmanager put-secret-value \
  --secret-id pihole/api-password --secret-string 'new-value'
```

`test`/`test` is LocalStack's standard placeholder — it doesn't validate
credentials by default.

like Secrets Manager. `3.0` boots with no token required.

**Cluster-side sync**: the `ase-market-helm` namespace's `ase-market-helm-ase-credentials`
Secret can be kept in sync with a `secretsmanager` entry here via a small
CronJob (image: [`../secrets-sync`](../secrets-sync), source of the
`aabutouq/secrets-sync` image) rather than a full External Secrets Operator
install — see `secretsSync` in [`../helm/ase-market/values.yaml`](../helm/ase-market/values.yaml)
(disabled by default until this host's LocalStack is actually deployed and
seeded). Note it only polls on a schedule and writes a plain Secret — pods
read Secret-sourced env vars once at container start, so a rotated value
still needs those pods restarted to take effect.
